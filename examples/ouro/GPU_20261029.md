# Single-GPU Ray service and online N+2 reference — 2026-10-29

A registered standalone Ray replica now runs real Ouro-1.4B token generation
through verl's LLMServerClient and SingleTurnAgentLoop. Cancellation, full policy
publication, failure fencing and fresh-actor recovery pass on one GPU. This
qualifies the serving boundary; the distributed trainer/AgentLoopManager loop is
not yet connected or accepted.

The N=1 -> N+2=3 predictor now loads a trained artifact and makes real online
execution decisions in an opt-in serial native reference. Its selected depth is
actually executed before coda, and shallow exits finalize last-exited KV. On two
small arithmetic holdouts, the learned policy offers no advantage over fixed
three-loop execution or the original gate. These negative comparative results
are retained; no production N+2 policy or batching speedup is claimed.

## Ray standalone increment

Import `examples.ouro.ray_server` explicitly to register `OuroReplica` under
`vllm_rlt` in verl's separate RolloutReplicaRegistry. The existing BaseRollout
adapter remains available independently. The replica supports one GPU per
standalone replica, including placement in a supplied resource pool. The tested
allocation is a direct Ray one-GPU allocation; resource-pool placement has not
been exercised by this campaign.

`OuroTokenServer` owns one public StageClient request/control endpoint. All
add/step/abort/publication/cache/close calls execute on one actor event-loop
owner. It yields between complete native steps so cancellation can progress;
it does not share a pipe or CUDA owner across arbitrary executor threads.
A native step is synchronous, so its duration bounds responsiveness.

| Real GPU/Ray check | Result |
| --- | --- |
| Fresh actor before publication | Generation rejected |
| Two concurrent framework-client requests | 16 tokens each; aligned raw scores and actual depths |
| Effective seeds and provenance | Seeds 17/18, committed version 1, optimizer step 0 preserved |
| In-flight abort | Native request retired; caller receives failure |
| Duplicate tensor stream during publication | Failure consumes version 2 and keeps admission closed |
| Full retry | Real backend commits version 3 |
| Fresh actor and restored counters | Remains fenced until full republication commits version 4 |
| Before/after restart | Tokens, depths and selected scores exactly equal; actor epoch differs |
| SingleTurnAgentLoop and `as_dict()` | Depth/seed/version metadata retained |
| Final request/KV ownership | Zero active requests and zero used blocks |

The SingleTurnAgentLoop test uses the default Continuous Token builder with an
explicit plain text template for this non-chat checkpoint. It validates a
single text turn, not tools, multimodal requests or arbitrary chat templates.
`TokenOutput.extra_fields` carries actual depth, effective sampling parameters,
raw probability profile, committed weight version, optimizer step and a unique
request generation. Optimizer steps are not reconstructed as version minus one.

FIFO admission/abort ordering and resume-during-publication draining each had a
failing CPU regression before their fixes. A failed update cannot reopen
admission through `resume_generation`. Restore retains monotonic publication
counters but does not claim weights have been restored; fresh full publication
is required. The base model/optimizer checkpoint remains the trainer's job.

Hybrid/colocated memory switching, HTTP serving, P/D replicas, multi-replica
publication acknowledgement, full AgentLoopManager/trainer conversion and
fault-tolerant distributed training remain open. Unsupported memory switching
and topology modes fail explicitly. Registration alone does not complete Phase 2A.

## N+2 data, loading and execution

The frozen full-depth teacher collects 16 decode-input states per prompt. At
loop 1, a linear head predicts whether loop-3 cumulative hazard is at least 0.5.
There are 48 training prompt groups (768 states), 16 validation groups (256
states), and two independent 24-prompt test sets. Train/validation operands
`a=1..8` do not overlap test operands. Feature normalization uses training states
only. The head trains for 300 AdamW steps with seed 19; label and decision
thresholds are fixed at 0.5 before either test set.

Validation accuracy is 242/256 (94.53%), versus 235/256 (91.80%) for the training
majority prediction; there is one false positive and 13 false negatives. This
is an imbalanced teacher-hazard classification task, not answer-quality training.
The teacher uses full-depth KV; the online policy instead consumes the states
created by its actual exited trajectory.

The artifact stores source/target depths, loop count, model revision, mean,
scale and linear weights. Loading rejects mismatched model/depth metadata,
nonfinite tensors, incompatible shapes and invalid scaling. The head and full
teacher traces are release assets, not model weights committed to Git.

`nplus2.generate` is an explicit serial reference using the native public
`prelude`, `recurrent`, `coda` and KV `finalize_token` operations. Prompt prefill
runs four loops; the first response therefore has depth 4. For each later decode
input, the loop-1 decision selects depth 3 or 4, execution reaches that depth,
then the chosen hidden state produces the next token. KV is finalized before
the next input. No loop-1 hidden state substitutes for the loop-3 output.

Forced-positive and forced-negative controls exactly match fixed-depth 3 and
full-depth outputs/scores, respectively. An independent StageEngine trace-mode
control matches all five response tokens, execution depths and raw selected
scores with maximum error 0. This is a short matched-prefix correctness control,
not a new claim of whole-model train/inference numerical parity.

## Matched quality and serial timings

All modes use BF16/Triton, greedy decoding and 16 forced output tokens at
concurrency 1. The original gate retains its native minimum of two loops.
Two unprofiled passes reverse policy order. Each request includes fresh KV
allocation, prefill and decode; model load and warmup are excluded. These are
serial reference request timings, not serving throughput or high-concurrency
measurements. The correctness metric is the first generated integer matching
the arithmetic answer. Complete sequences can differ despite matching answers.

| Test set / policy | Correct / 24 | Mean decode-input depth | Aggregate output tok/s |
| --- | ---: | ---: | ---: |
| Small held-out operands / full | 24 | 4.000 | 23.61 |
| Small held-out operands / fixed 3 | 24 | 3.000 | 30.70 |
| Small held-out operands / original gate | 24 | 3.106 | 29.53 |
| Small held-out operands / N+2 | 24 | 3.181 | 28.91 |
| Harder operands / full | 23 | 4.000 | 22.50 |
| Harder operands / fixed 3 | 24 | 3.000 | 29.25 |
| Harder operands / original gate | 24 | 3.153 | 27.47 |
| Harder operands / N+2 | 23 | 3.308 | 26.11 |

Small holdout operands are `a=9,10,11; b=1..8`; the harder set uses
`a=17,29,53; b=13,17,23,29,31,37,41,47`. Operations include addition, subtraction
and multiplication. The same head and thresholds are used on both sets.
Greedy token sequences repeat exactly within each policy across both passes.

N+2 executes more loops than fixed 3 and the original gate on these workloads,
and adds head normalization/projection and a decision readback. Its lower
throughput is consistent with that added work; the measurements do not isolate
an exact wall-time decomposition. On the harder set it also misses the answer
fixed 3 and the original gate obtain. This head/reference does not justify a
production merge. Broader tasks, calibration, trajectory-aware labels and an
actual batched lookahead implementation remain necessary.

Separate ops-only and full-detail CUDA profiles each contain 36,111 CUDA kernel
events. Their times are excluded from the table. Full detail enables shapes,
memory and stacks. Profiles are diagnostics for this serial execution path.

## Verification, reproduction and next hardware boundary

Final CPU adapter suites: #78 **110 passed / 22 skipped**; #83 **96 passed /
36 skipped**. Publication-dependent cases correctly skip on #83. The 13 new CPU
cases cover loaded predictions, actual-depth replay, native gate minimum,
request lifecycle, registry dispatch, FIFO, restore and publication draining.
All 14 repository pre-commit hooks pass. CPU skips do not qualify GPU behavior.
The raw result audit checks both eight-run evaluation sets, profiles, actual
selected/executed depths, all Ray controls and the independent trace oracle.

Use the existing image/runtime setup, then install the additive client imports:

```bash
uv pip install --python /path/to/venv/bin/python --no-deps \
  -r examples/ouro/requirements-ray.lock
export PYTHONPATH=/path/to/pr78:/path/to/verl
```

The release contains executable `run_nplus2.py`, `run_ood.py`, `run_ray.py` and
`run_ray_agentloop.py` with frozen arguments. Set their task-root paths explicitly
before reproducing. They do not start training ranks or a P/D topology.

[Selected JSON and check logs](results/2026-10-29) accompany this report. The
[complete evidence prerelease](https://github.com/Levius-Fubuki/verl/releases/tag/ouro-single-gpu-evidence-20261029)
contains raw runs, failed controls, source manifests, predictor/teacher tensors,
profiles, scripts and checksums. Model weights and task venv are excluded.

During the sampled Ray/harder-holdout portion, peak whole-device usage was
4,236 MiB. The online reference reports a 2.884 GiB allocated / 3.131 GiB reserved
allocator peak in the harder-holdout process. Sampling did not cover the initial
teacher collection, and these observations do not establish a strict minimum
VRAM capacity or validate ordinary 24 GB hardware.

The next dedicated Ray training topology needs **three GPUs**: two FSDP ranks
plus one independent rollout replica. Three 48 GB-class cards preserve the
already tested trainer memory margin. Dedicated prefill and decode alongside
those ranks would require four devices. One GPU can still support predictor
improvements and single-replica work; three GPUs are not a dependency of N+2
head training itself. Unified #78/#83 acceptance remains an upstream interface
integration item, not a GPU-capacity issue.

contributor-fork draft for human line review and independent testing, with no
upstream verl submission or production-readiness attestation.
